這組測試涵蓋三項不同責任：原生錯誤路由（native error routing）必須拋出不屬於 SCNSim 的失敗，並把方程式失敗留作證據；每個方程式的證書（certificate）必須從已編譯的程式完整回傳；線性求解診斷（solve diagnostics）必須描述實際回傳的解。錯誤路由與證書案例都在已編譯的程式內求解一個小型帶狀系統，不會求解物理電路。

## 原生錯誤路由（Native error routing）

已編譯的程式除了回傳數值，還會回傳兩類失敗。方程式失敗是證據：分析會依狀態值把它回報為具型別的失敗，所以主機端不得拋出它，也必須讓它的證書維持原樣。不屬於 SCNSim 的檢查一旦失敗，代表內部的不變條件遭到破壞，所以主機端必須以原本的訊息與 cause 把它拋出。

路由案例在下一節的四節點帶狀系統上執行已編譯的程式。奇異矩陣會使方程式失敗；以 JAX 的 `checkify.check` 寫成的檢查，則代表不屬於 SCNSim 的檢查。這個方程式屬於某個響應（response），失敗時的狀態（status）為 7。

1. 讓方程式在單一程式、批次程式的部分通道（lane），以及循序映射的 Newton 迴圈內失敗。此時不會拋出任何錯誤，回傳證據的每個陣列逐位元不變，證書列仍然指明所屬的響應，並且只在失敗的通道記錄狀態 7。
2. 讓不屬於 SCNSim 的檢查單獨失敗、在某個通道失敗、與方程式失敗分處不同通道，以及在循序映射的迴圈內失敗。它會以 JAX 的執行期錯誤（runtime error）拋出，訊息與 cause 和程式本身拋出的相同。沒有任何失敗的程式不會拋出錯誤。
3. 傳入經過包裝的失敗。批次程式的失敗由 JAX 包裝，循序映射迴圈的失敗由 SCNSim 包裝。只有包裝內全部都是方程式失敗時，它才算方程式失敗；空的、通道標示錯誤的或內容被截斷的包裝一律遭拒。

這些案例可抓出被吞掉的原生錯誤，以及包裝層把無法解讀的錯誤誤認為已知錯誤的情形。來源：[test_native_failure_routing.py](../test_native_failure_routing.py)。

## 編譯程式回傳的方程式證書（Equation certificates）

SCNSim 求解的每個方程式都會回傳一份證書（certificate）：狀態（status）、後向殘差（backward residual）`eta` 及其分子與分母，以及該次求解是否實際執行。這組案例在已編譯的 JAX 程式中求解一個四節點的帶狀複數系統，再把證書逐列讀回。每一列以角色（role）、階段（stage）、導數階數與相依項（dependency）識別。

| 案例 | 各列必須呈現的內容 |
| --- | --- |
| 已解、失敗、略過與未執行 | 未執行的方程式標示為不存在：status 為 0，殘差數值為 NaN。因先前失敗而略過的求解帶有該失敗的 status，並標示為未執行求解。奇異矩陣以其方程式的 stage 作為 status，殘差數值為無限大。 |
| `cond`、`while_loop` 與 `scan` | 每個方程式只保留一列。未選取的分支與一次也沒有執行的迴圈，會使該列不存在。迴圈回報第一次失敗；沒有失敗時，回報最後一次執行。 |
| `vmap` | 每一列在每個批次通道（lane）各有一個項目。通道在它未選取的分支中不存在。 |
| 導數方程式 | 反向模式（reverse mode）增加伴隨（adjoint）列，前向模式（forward mode）增加切線（tangent）列，二階前向導數增加混合（mixed）列，頻率 jet 增加頻率切線（frequency tangent）列。原始方程式失敗時，它的導數方程式會被略過。 |
| 導數可用性 | 零空間向量圖表（null-vector chart）只在它的導數規則實際執行之處記錄導數是否可用，並附上相依項與原因；每個通道分別記錄，反向模式下也會保留。 |
| 循序映射的 Newton 迴圈 | 各通道在不同的迭代次數後停止，其中包含一次也沒有執行的通道與失敗的通道；它們的列仍帶著通道軸回傳。 |
| 單精度 | complex64 運算元的證書數值維持 float32，全域 x64 設定不變。 |

這些案例不斷言任何容許誤差，只檢查 status 代碼、「已執行」與「存在」兩個旗標，以及殘差數值是有限、無限大、NaN 還是恰為零。右手邊為零時殘差恰為零，由此可以看出迴圈回報的是哪一次迭代。

另有一個獨立的測試記錄每一列的來源位置（site）標籤，以及各列回傳的順序。`site` 是方程式在追蹤程式中的位置，JAX 自身的方程式也計算在內，所以其他案例都不依賴它。來源：[test_certificate_transport.py](../test_certificate_transport.py)。

## 證書帳本（Certificate ledger）

SCNSim 正把這些證書從 JAX 內部的檢查機制，移到自己的證書帳本（ledger）：它是已編譯程式的一般輸出，每個方程式在其中各有一筆紀錄。遷移完成之前，兩種回傳證書的方式並存，各項分析仍使用前者。帳本由兩組案例涵蓋。

第一組把上一節的每一次呼叫都用兩種方式編譯，並要求結果相同：各列的數目、順序與標籤相同，每一列的六個陣列逐位元相同，回傳值相同，導數可用性的紀錄也相同。另外增加的呼叫，涵蓋循序映射的 Newton 迴圈位於自訂導數規則之下、位於分支之內、處於反向模式，以及位於另一個循序映射的迴圈之內。有兩種情形，兩者除了 `site` 之外完全相同：兩種機制在追蹤程式中各自加入的方程式數目不同，所以排在後面的方程式位置不同；這些案例同時記錄兩邊的標籤。來源：[test_certificate_transport_parity.py](../test_certificate_transport_parity.py)。

第二組涵蓋比對無法呈現的性質。

| 案例 | 必須成立的事 |
| --- | --- |
| 公開介面 | 帳本所在的模組只匯入 JAX 的公開模組，不讀取任何私有屬性。 |
| 帳本無法取得的方程式 | 方程式若位於帳本沒有規則的 JAX 基本運算（primitive）之內，或位於迴圈的判斷式之中，編譯會以具型別的錯誤停止；它的證書不會無聲遺失。 |
| 每個方程式一筆紀錄 | 一筆紀錄保留第一次失敗；沒有失敗時，保留最後一次執行。 |
| 未執行的程式 | 它的帳本只由形狀建立，每一筆紀錄都標示為不存在。不存在的導數可用性紀錄讀作「可用」，所以只有存在的紀錄才能使導數不可用。 |
| 單精度 | complex64 方程式的紀錄維持 float32，不論存在與否。 |
| 帳本作為資料 | 帳本經過後續的已編譯呼叫後內容不變；取出單一通道的切片，等於單獨計算該通道所得的帳本。 |
| 不屬於 SCNSim 的檢查 | 這類檢查帶著原本的訊息回傳。方程式失敗絕不會被當成這類檢查回傳，現行機制也照常記錄它所認證的程式。 |
| 隨數值傳遞的紀錄 | 把紀錄附在數值上的兩個運算，在已認證的程式之外原樣回傳該數值；它們的導數規則原樣回傳切線（tangent）與餘切向量（cotangent）。 |

來源：[test_certificate_ledger.py](../test_certificate_ledger.py)；導數規則見 [test_differentiation_rules.py](../test_differentiation_rules.py)。

## 分析如何使用回傳的證據

各項分析不會直接讀取已編譯程式所回傳證據的內部，不論證據是以上述哪一種方式回傳。它們只透過一小組操作使用證據：取出單一通道、建立未執行程式的證據、在程式內詢問是否有任何失敗、只保留某個根的紀錄、讀出證書列與導數可用性的紀錄，以及拋出不屬於 SCNSim 的檢查。這些案例在同一個四節點系統上，涵蓋只有這些操作才能呈現的行為。本節所稱的框（frame），是指一個已編譯的程式連同它回傳的證據。

| 案例 | 必須成立的事 |
| --- | --- |
| 依序執行的頻率分塊（chunk） | 第一個失敗的頻率點之後，分塊內其餘的點不會執行，它們的列標示為不存在。同一批點若當作互相獨立的通道計算，則全部存在。 |
| 未執行的框 | 它的證據只由形狀建立：每一列與每一筆導數可用性的紀錄都不存在，沒有任何失敗，也不會拋出錯誤。 |
| 在程式內看到的失敗 | 任何一個通道的方程式失敗都算失敗；因先前的失敗而被略過的方程式也算。 |
| 已完成的根 | 一個框若求解多個根，可以把其中一個根的列單獨分出來。後續的框從已完成的根接續計算時，該根的列不論成功或失敗，都逐位元出現在後續框的證據中，與它自己的列並列。 |
| 證據作為資料 | 證據經過後續的已編譯程式後內容不變。從批次證據取出單一通道，等於單獨計算該通道所得的證據；有兩個通道軸時也成立。 |
| 框的順序 | 三個頻率、每個分塊兩個頻率的靈敏度計算，會依執行順序列出各框的列：先是不含導數方向的框，再是該方向的框，各自依工作順序排列。 |
| 不屬於 SCNSim 之檢查的訊息 | 拋出的文字就是該檢查的文字，並帶有傳入的數值。檢查若位於含多個通道的循序映射迴圈內，文字會列出每個通道的數值。 |
| 方程式失敗與不屬於 SCNSim 的檢查同時出現 | 讀取結果的一方一律拋出該檢查。直接取用呼叫所回傳證據的一方，則依先發生的失敗決定，所以較早的方程式失敗會蓋過該檢查。證書帳本把這類檢查分開存放，這項差異會隨之消失。 |
| 誰讀取證據 | 掃描套件原始碼的結果：只有兩個模組讀取證據的內部，即回傳證書的模組與提供上述操作的模組。 |

來源：[test_frame_evidence.py](../test_frame_evidence.py)。

## 求解診斷（Solve diagnostics）

小型單位矩陣案例會區分彙總指標與方程分量診斷。令 `A = I₂`、一個右手邊（right-hand side）向量 `b = [1, 1e-20]`、近似解 `x = [1, 0]`；彙總正規化殘差為 `5e-21`，第二個方程分量（equation component）的殘差則為 1。彙總指標符合原有求解器門檻，但逐右手邊（per-right-hand-side, per-RHS）診斷會指出該分量的錯誤。另一個兩欄案例才是兩個右手邊，檢查值為 `[1, 0]`，其中第二個解欄完全正確。

1. 稠密（dense）案例將診斷與實際原始解比較。
2. 稀疏（sparse）與補償求解（compensated solve）路徑保留原解及四個輔助純量。

測試確認診斷欄位描述實際執行的求解，不新增門檻，也不讓彙總掩蓋不正確的分量。來源：[test_solve_diagnostics.py](../test_solve_diagnostics.py)。
